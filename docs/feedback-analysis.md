# Анализ отзывов с подтверждающими источниками

После миграции `AddFeedbackAnalysis` фоновый `FeedbackAnalysisWorker` обрабатывает
существующие и новые непустые комментарии. Сохраняются результаты по каждому ID,
исходный текст, версия модели/промпта/каталога, статус, число попыток и время повтора.
Автор, группа и оценки студента в модель не отправляются; в самом комментарии могут
присутствовать персональные сведения. Идентичные комментарии разных отзывов не
объединяются и не считаются независимыми подтверждениями одного события.

На каждый фрагмент выполняются два вызова: извлечение тем и отдельный поиск
серьёзных сигналов. Это два прохода модели, а не независимые свидетельства.
Длинные комментарии разбиваются по 6000 символов с перекрытием 500, хвост не
отбрасывается. Точные цитаты проверяются кодом; выдуманные фрагменты, неизвестные
ID категорий и некорректный JSON приводят к ошибке обработки и повтору. Проверка
наличия цитаты не доказывает правильность её интерпретации моделью.

Каталог передаётся в каждый вызов с описаниями категорий. Модель использует
существующий ID или предлагает название и описание новой категории, подкреплённые
цитатами. Предложение сохраняется в результатах, но не становится категорией без
действия администратора. Одинаковые названия нормализуются; смысловые дубли
проверяет администратор. Добавление категории меняет версию анализа и запускает
повторную обработку. При обновлении каталога старые сведения из неизменённых
комментариев остаются видимыми, а покрытие помечается неполным.

## API (только Admin)

- `GET /api/Summaries/teacher/{id}?periodId=…&startYear=…`
- `GET /api/Summaries/discipline/{id}?periodId=…&startYear=…`
- `GET /api/Summaries/categories`
- `POST /api/Summaries/categories` — `{ name, description, requiresAttention }`
- `PUT /api/Summaries/signals/{feedbackId}/{signalKey}` — `{ status, note }`

Сводка теперь возвращает `FeedbackReportDto`, **вместо строки**. API и frontend
нужно выпускать совместно. Отчёт включает покрытие, темы с точными количествами,
источники `feedbackId + quote`, серьёзные сигналы и предложенные категории. Он не
кэшируется, поэтому прогресс фоновой обработки виден после обновления.

Частоты считаются по уникальным ID отзывов. Один отзыв может относиться к нескольким
темам и содержать обе оценки одной темы. Краткий обзор составляется из подсчётов
кодом; свободная генерация утверждений поверх агрегатов не используется.
Серьёзные сигналы включаются отдельно от популярных тем, даже при единичном
упоминании и частичном сбое анализа. Их наличие не устанавливает факт нарушения.

Рассмотрение хранится отдельно: `Pending`, `InReview`, `Reviewed`. Для `Reviewed`
нужна заметка о результате. Сигнал привязан к тексту источника и цитате. Изменённый
отзыв требует нового анализа; старые цитаты не показываются. Удалённые отзывы не
участвуют в отчёте. На frontend каждый источник открывается по `/feedback/{id}`
через существующий авторизованный `GET /api/Feedback/{id}`. Категории и заметки
рассмотрения не меняют исходный студенческий отзыв.

## Настройка и запуск

`AI:AnalysisEnabled` (по умолчанию `true`) включает обработку всех накопленных
комментариев, включая периоды без открытого сбора. Планируйте два вызова на фрагмент
при первичном заполнении и при смене модели/промпта/каталога.
`AI:AnalysisPollSeconds` = 15, `AI:RequestTimeoutSeconds` = 90. Можно отключить worker,
сохранив доступ к уже подготовленным отчётам. Фоновая задача последовательно
обрабатывает отзывы; PostgreSQL advisory lock предотвращает повторные вызовы из
разных реплик. При ошибке — повтор с увеличивающейся задержкой до 60 минут.

Миграции в production применяются существующим migration Job перед запуском API.
Для проверки без реального провайдера есть `FeedbackAnalysisModelTests`: один
сигнал среди 200, точные ссылки, противоположные оценки, неполное покрытие,
предложения категорий, редактирование источника. Эти тесты проверяют конвейер;
полноту распознавания самой модели следует измерять на размеченных русскоязычных
отзывах отдельно.
